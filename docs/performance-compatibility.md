# Performance-only compatibility contract

The user's requirement is to preserve existing functionality while improving performance. The pre-optimization report baseline is commit `429eedcd6dc29fa02c061257c2e418d764f3ee40`. Earlier performance measurements remain evidence for their specific workloads; passing tests cannot prove correctness for every possible export.

## Executable baseline

`tests/compatibility/baseline-v2.json` contains complete reports generated by the pinned commit's parser, scope and statistics modules. The generator imported a frozen `git archive` of that commit, not the current production modules. Fixtures are synthetic and defined independently in `tests/compatibility/fixtures.ts`. The clock is fixed to `2025-02-01T12:00:00.000Z`; no report fields, array order or warnings are removed from comparison.

The test also pins the baseline file's SHA256, `b8db49562494378628f90149fd38fa1b2649c221a18c48dceb04f9a7b06f3684`, so an accidental snapshot rewrite fails independently of report comparisons.

The 22 scenarios cover current/all branches, user/dialogue/all roles, groups enabled/disabled, year comparison with/without prior data, UTC/Shanghai/New York/Kiritimati/Adak, spring/fall DST, inclusive custom dates, empty data, anomalous spans, partial damaged shards, missing/cyclic branch links, overlapping shards, attachments with richer duplicate metadata, linked/unscoped feedback, library files, shares, archives/stars and long text with repeated/high-cardinality terms. Three additional cases pin errors for missing, broken and invalid main data.

For each successful scenario the test compares:

- Every field of the complete report, including distributions, rankings and their tie order, keywords, warnings, schema/options and previous-year comparison.
- Report restore and local-storage round trips.
- Exact UTF-8 SHA256 of reopenable JSON, full-data JSON and saved JSON, plus the compaction flag.
- Exact SVG hashes for both languages and all four keyword/title privacy combinations: 176 SVG comparisons across the scenarios.

These compatibility checks run automatically as part of `npm test`, including in the existing three-browser CI matrix. Run them separately with:

```sh
npm run test:compatibility
```

Existing tests additionally cover limits, storage failures, corrupted report schemas, cancellation, stale worker responses, PNG generation, keyboard/touch navigation, all fourteen report pages, accessibility and mobile layouts. Pages continues to depend on all CI browser checks. Large-data changes must also compare full 510,000-message reports; tests and the source ZIP contain no real chat exports.

## Rules for later optimization

Do not regenerate the expected baseline, remove assertions, hide fields or relax import/validation/privacy rules to make an optimization pass. A compatibility failure blocks that optimization. An explicitly authorized feature change needs separate documentation and a deliberate contract update.

Performance evidence must distinguish first import, repeated calculation, timezone changes, long messages, attachment-heavy data and narrow date selections. Report time and memory separately and retain slower cases. A gain in one path does not establish that every input is faster.

The earlier special-ID association correction and other authorized functional fixes remain separately protected by existing regression tests. They are not classified as pure performance improvements; later changes must preserve those corrected behaviors too.

Historical comparison found a regression introduced in `3f2bcc5`: an unchanged attachment in an overlapping shard could lose its inferred extension in the exported largest-attachment metadata. Counts remained unchanged. This change restores the original extension-enrichment behavior by visiting only pending attachment-message lists once per overlap, without re-parsing all unchanged messages or inserting duplicate assets. Four focused cases cover an original attachment, a newly introduced attachment, the next overlap and explicit metadata taking precedence over inferred suffixes. The report baseline is generated from `429eedc`, so this correction must match original output rather than a regenerated optimized result.

The historical audit compares 22 complete-report scenarios and three rejection cases for each of `429eedc`, `3f2bcc5`, `8967f09` and the repaired source: 100 comparisons in total. The repaired source matches the original baseline in all 25 comparisons. The four historical mismatches are the same extension loss in two overlapping-shard scenarios in each of `3f2bcc5` and `8967f09`; they are recorded as a regression, not accepted as a performance tradeoff.

No new performance optimization or UI/style change is included in this compatibility repair.

The repaired build also passed the 510,000-message Chromium fixture: both complete reports (UTC/all years and 2025/Asia/Shanghai) equal retained pre-repair snapshots except generation time, and the previous-year comparison matches. This run took 14.92 s to import and 8.58 s to recalculate; the previous run took 12.53 s and 8.03 s. These individual runs do not prove a speed improvement or quantify the repair's overhead; the earlier timing-variability notes still apply. Correctness restoration and an executable compatibility contract are the purpose of this change.
